# Spec: User Profile Memory

## Overview

Atlas builds a persistent, fact-based profile of the user from everything they write — journal entries, mentor conversations, daily check-ins — and injects the relevant slice of it into every AI system prompt in the app. The model is Claude's own memory: discrete facts with provenance and dates, not a rewritten narrative blob.

Today `mentor_context.about_me` is a 2,602-character document that only the Mentor chat writes (full-document rewrite by Haiku after every reply over 150 chars) and only two of 22 AI routes read. Journal entries contribute nothing. This spec replaces that entirely.

**Design decisions already locked:**

1. Extraction runs per-entry on write, plus a lazy consolidation pass when the profile goes stale.
2. Facts are category-tagged and filtered per AI surface.
3. **No opt-in/opt-out.** Everything the user writes is ingested. Users writing into an AI journal expect it to be remembered. Scoping is what keeps a relationship fact out of a gym-set reply, not user choice.
4. The existing `about_me` blob is decomposed into seed facts, then retired.
5. `mentor_memories` is dropped; identity content becomes facts, conversational recency comes from `mentor_conversations` / `mentor_messages`.

---

## Stack Context

- Next.js App Router v16.2.6 + TypeScript, Tailwind v4, TanStack Query v5
- All DB access in API routes uses `createServiceClient()` (RLS bypassed, per-user scoping enforced in code). `createClient()` is auth-only.
- AI clients resolve per-user via `getAnthropicForUser(userId)` from `src/lib/anthropic.ts`, returning `null` when the user has no key. Every AI route returns `noKeyResponse('anthropic')` in that case.
- Background work uses `after()` from `next/server` (already the pattern in `src/app/api/mentor/chat/route.ts`).
- Extraction and consolidation use `claude-haiku-4-5-20251001`. Never Sonnet — this runs on every write.
- Migrations live in `supabase/migrations/` and are applied with psql against `DATABASE_URL` from `.env.local`.

## Database

### New table: `user_profile_facts`

Migration file: `supabase/migrations/20260728000001_user_profile_memory.sql`

```sql
create table if not exists user_profile_facts (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users(id) on delete cascade,
  category text not null,
  tier text not null default 'durable',
  content text not null,
  source_kind text not null,
  source_id uuid,
  status text not null default 'active',
  first_seen_at timestamptz not null default now(),
  last_confirmed_at timestamptz not null default now(),
  expires_at timestamptz,
  created_at timestamptz not null default now(),
  constraint user_profile_facts_category_check check (category in (
    'identity','goals','training','nutrition','health',
    'relationships','work','values','preferences','struggles'
  )),
  constraint user_profile_facts_tier_check check (tier in ('durable','state')),
  constraint user_profile_facts_status_check check (status in ('active','archived','pinned')),
  constraint user_profile_facts_source_kind_check check (source_kind in ('journal','mentor','checkin','seed','manual'))
);

create index if not exists user_profile_facts_user_active
  on user_profile_facts (user_id, status, category);
create index if not exists user_profile_facts_user_source
  on user_profile_facts (user_id, source_kind, source_id);

alter table user_profile_facts enable row level security;
create policy "Users access own profile facts" on user_profile_facts
  for all using (auth.uid() = user_id);
```

Field notes:

- `tier` — `durable` facts accumulate and persist ("trains 4-5x/week", "graduated in June, in a transition period"). `state` facts are the rolling emotional/situational weather from the last 14 days; they carry `expires_at` and get fully regenerated by consolidation rather than accumulating. Without this split the profile degrades into a mood log and every coach opens with "given how drained you've been."
- `status` — `pinned` facts are user-protected and never archived by consolidation. `archived` facts stay in the table for provenance but are excluded from prompts.
- `last_confirmed_at` — bumped when a new entry restates an existing fact. Drives staleness ranking during consolidation.

### Changes to existing tables

```sql
alter table journal_entries add column if not exists profile_ingested_at timestamptz;
alter table mentor_context add column if not exists last_consolidated_at timestamptz;
```

`profile_ingested_at` makes ingestion idempotent. An entry is ingested when `profile_ingested_at is null or updated_at > profile_ingested_at`, which also handles edits.

Do **not** drop `mentor_context.about_me` in this migration. It is the seed source. Drop it in a follow-up migration once seeding is verified (see Rollout).

### Table to drop

`mentor_memories` — after the seed pass. See "Mentor cleanup" below for the blocker in `activity-snapshot`.

### `src/lib/profile/getProfileBlock.ts`

```ts
export async function getProfileBlock(
  db: SupabaseClient,
  userId: string,
  surface: ProfileSurface,
): Promise<string>
```

Behaviour:

1. Select active + pinned facts for the user, filtered to the surface's categories, excluding `state` facts whose `expires_at` has passed.
2. If `mentor_context.last_consolidated_at` is null or older than 7 days, fire `after(() => consolidateProfile(db, userId))`. Never await it. Never block the response.
3. Render to a plain text block and return it. Return `''` when there are no facts, and callers push nothing onto their prompt in that case.

Render format:

```
WHO THIS USER IS:
[identity] Graduated in June 2026, in a deliberate transition period. (since Jun 14)
[training] Trains 4-5 sessions per week, rest day usually Tuesday. (confirmed Jul 22)
[struggles] Nutrition is the consistent weak point, especially protein on non-training days. (confirmed Jul 22)

RIGHT NOW (last 14 days):
Pushing hard on the cut and frustrated with the pace of visible change.
```

Dates come from `first_seen_at` for stable identity facts and `last_confirmed_at` for behavioural ones. Include them — dated facts stop the model from asserting stale things as present tense.

Cap the block at roughly 40 durable facts, ranked by `status = 'pinned'` first, then `last_confirmed_at` descending. If the cap trims anything, that is a signal consolidation is overdue, not a reason to grow the prompt.

### `src/lib/profile/extractFacts.ts`

```ts
export async function extractFacts(
  db: SupabaseClient,
  userId: string,
  input: {
    sourceKind: FactSourceKind
    sourceId: string | null
    content: string
    occurredAt: string   // ISO, the entry/conversation timestamp
  },
): Promise<void>
```

Behaviour:

1. Resolve the Anthropic client with `getAnthropicForUser(userId)`. If null, return silently. This runs in background, so a missing key is a no-op, never an error surfaced to the user.
2. Load the user's current active durable facts (id + category + content only, to keep the prompt small).
3. Single Haiku call. Pass the existing facts and the new content, ask for structured JSON. Passing the fact list inline gives dedupe without embeddings.

Expected response shape:

```json
{
  "new": [{ "category": "training", "tier": "durable", "content": "..." }],
  "confirms": ["<fact-id>", "<fact-id>"],
  "contradicts": [{ "id": "<fact-id>", "replacement": "..." }]
}
```

4. Apply: insert `new` rows with the given `source_kind`/`source_id` and `first_seen_at = occurredAt`; bump `last_confirmed_at` on `confirms`; for `contradicts`, archive the old row and insert the replacement carrying the original's `first_seen_at`.
5. Wrap everything in try/catch. Log and swallow. A failed extraction must never break the journal save or the mentor reply.

Prompt requirements for the extractor, spelled out because the current implementation gets these wrong:

- Extract only what the user actually stated or clearly implied. **Never infer scores, ratings, or grades.** The existing `about_me` claims "recovery capacity scores around 8.5/10" — nothing in the data produced that number, the model invented it once and every rewrite treated it as established.
- One fact per row, one sentence, third person, self-contained. A fact that only makes sense next to another fact is two facts or none.
- Prefer durable over state. Only classify as `state` when it is explicitly about the current moment or a recent stretch.
- Return `{"new":[],"confirms":[],"contradicts":[]}` when an entry contains nothing worth remembering. Short entries usually do.
- Do not extract raw metrics that live in the database. "Benched 185 for 8" is a `gym_logs` row, not a profile fact. "Treats bench press as his benchmark lift" is a profile fact.

### `src/lib/profile/consolidateProfile.ts`

```ts
export async function consolidateProfile(
  db: SupabaseClient,
  userId: string,
): Promise<void>
```

Runs lazily from `getProfileBlock` when the profile is over 7 days stale. No cron, no `vercel.json`, no `proxy.ts` bypass needed.

1. Load all active + pinned durable facts, plus the last 14 days of journal entries (`body`, `audio_transcript`, `mood`) and check-ins.
2. One Haiku call to merge near-duplicates, archive facts contradicted by recent content, and rewrite anything that has drifted. Pinned facts are passed as read-only context and never modified.
3. Second Haiku call to regenerate the `state` tier from the 14-day window. Delete all existing `state` rows and insert fresh ones with `expires_at = now() + 14 days`.
4. Set `mentor_context.last_consolidated_at = now()`.
5. Try/catch around the whole thing. On failure, leave `last_consolidated_at` untouched so the next read retries.

### `src/lib/profile/ingestJournalEntry.ts`

```ts
export async function ingestJournalEntry(
  db: SupabaseClient,
  userId: string,
  entryId: string,
): Promise<void>
```

Idempotency wrapper around `extractFacts` for journal entries:

1. Load the entry. Bail if it does not belong to `userId`.
2. Bail if `profile_ingested_at` is set and `updated_at <= profile_ingested_at`.
3. Build content with `entryContentForAI(entry.body, entry.audio_transcript)` from `src/lib/journalAudio.ts`. Bail if empty — voice entries with no transcript yet get picked up by the transcribe hook instead.
4. Call `extractFacts` with `sourceKind: 'journal'`, `sourceId: entryId`, `occurredAt: entry.date`.
5. Set `profile_ingested_at = now()`.

## Seeding the existing profile

One-off script: `scripts/seedProfileFacts.ts`.

1. Read `mentor_context.about_me` for each user that has one.
2. One Sonnet call (this runs once, quality matters more than cost) decomposing it into facts using the same schema and the same extraction rules.
3. **Drop every score, rating, grade, and evaluative judgment.** Keep only checkable statements about who the person is and what they do. The existing blob contains fabricated precision that must not be carried forward.
4. Insert with `source_kind: 'seed'`, `source_id: null`, `first_seen_at` set to `mentor_context.updated_at`.
5. Print the resulting facts to stdout for review before committing the transaction, or run in a `--dry-run` mode first.

## Rollout order

1. Run the migration. Add the table and the two columns.
2. Build `src/lib/profile/*` and the API routes.
3. Run the seed script in dry-run, eyeball the output, then run it for real.
4. Build `ProfileTab`, review the seeded facts in the UI, delete anything wrong.
5. Wire the extraction hooks.
6. Wire profile injection across the 18 routes.
7. Do the Mentor cleanup and repoint `activity-snapshot`.
8. Follow-up migration dropping `mentor_memories` and `mentor_context.about_me`.

Steps 3 and 4 come before 5 deliberately. The seeded profile should be reviewed by a human before anything starts writing on top of it.
